# Known Issues (backlog)

Found during the 2026-09-26 cleanup and while writing these docs, mostly by reading code. Unless marked **verified**, an item has not been reproduced in game: confirm it with a log before fixing (see [DEVELOPMENT.md](DEVELOPMENT.md#verifying-a-change-in-game)). Items are numbered for reference. Remove an item when it is fixed.

Fixed on 2026-09-26, for reference: `SkyrimNetDiaries_API.pex` had never shipped, so the theft decorator always returned None (**verified**, user report). Template lookup in `CreateDiaryBook` now uses `LookupByEditorID`, so powerofthree's Tweaks alone is enough (**verified**: before the change every creation failed without Native EditorID Fix). New entries for ESL and high load-order NPCs never reached a book: the event listener converted `actorFormId` with `as int`, which clamps FormIDs of `0x80000000` and up to `0x7FFFFFFF` (**verified**: "Could not resolve FormID 0x7FFFFFFF"). The listener now passes the JSON to the `UpdateDiaryFromEvent` native, which parses it in C++. Loading an older save built books before the player answered SkyrimNet's keep/clear prompt, so a Clear left a blank book behind and the next entry added a second volume 1 (**verified**, SkyrimNet and SNPD logs); the post-load sync now waits for the answer (`TimelineGate`), ignores diary events until it has run, and the stale-endTime rebuild removes the old books from the NPC's inventory. The save folder is now detected after those waits, so the previous save's DB is no longer picked up. Fixed on 2026-09-27: sealing or updating a volume, refreshing it on open and MCM Regenerate asked SkyrimNet for `EntriesPerVolume + 1` entries and treated them as the oldest, but SkyrimNet's limit keeps the newest, so when entries piled up behind a volume its first entries vanished from every book (`Database::GetVolumeEntries` now fetches the whole range and caps afterwards). The update query now passes the volume's boundary data, and the first overflow volume after a seal gets boundary data too, so an entry sharing the boundary date is no longer rendered in two volumes. Also fixed that day: an NPC could get two sets of volumes ("four diaries, each name twice", **verified**) because nothing tracked volumes still being created, so recovery, catch-up and diary events each created the same volumes; creations are now counted per actor and cancelled at every load and Reset. The create queue no longer stalls after a failed dispatch or when a load drops an in-flight Create(). DiaryDB is closed at kPreLoadGame, the co-save's folder name is ignored, a new game's first save marks its volumes persisted, volumes that reach past a loaded save are reconciled with the history SkyrimNet kept or cleared (ReconcileWithTimeline, replacing the game-time stale rebuild, which missed saved volumes after an in-session revert and dropped new entries), an empty template name no longer blocks an actor, and the actor cache and book timers hold FormIDs instead of pointers. Crash-proofing: exceptions can no longer escape into the engine from the book-open hook, the post-load sync (which now always re-enables diary events), the save and load callbacks, the theft event sink, the Papyrus natives, the inter-plugin handler or the SkyrimNet API wrappers. Config values are clamped when read, so EntriesPerVolume = 0 in the INI no longer hangs the game, and a non-numeric INI value no longer wipes the INI on the next save. Identity: theft and return detection work in every language (the English "Diary" name filter and the name-in-title owner fallback are gone; volumes are found by base FormID and owners by UUID), the Nightingale journal is chosen by base NPC instead of English name, a book opened after a load-order change no longer shows another actor's entries (the stored actor FormID is checked against the UUID), and the two startup warnings are localized. Text: dates use Skyrim's real month lengths instead of 30-day months; diary prose is escaped for the book markup (a "<" no longer swallows text, and a literal [pagebreak] can't shift the API's entry numbering); Win-1251 conversion only runs on Cyrillic text (French «» are no longer mangled) and now also maps „ and №; the inter-plugin API header describes what the handlers actually return. A volume whose entries were all deleted outside a load now shows the "all entries removed" page instead of its old text; a failed SkyrimNet query (now reported separately from zero entries) keeps the cached text. A New Game started after loading a save now ends the session like a load does (before, it kept writing into the previous character's DiaryDB). Lowering EntriesPerVolume no longer cuts entries from existing volumes: a volume's size comes from its stored boundaries. A failed query no longer makes ReconcileWithTimeline delete volumes or MCM Regenerate render the "all entries removed" page. Loading an earlier save drops only the thefts made after it (by `stolen_at`), not all of an actor's thefts; `last_known_game_time` is no longer used. A load or new game during the catch-up scan drops the rest of the scan instead of creating duplicate volumes. A recycled FormID the same actor already owns is now rejected too, and a new volume's text is written to the volume just registered, not the first one with that FormID. If the post-load sync can't load this save's volumes (no save folder, no DPF, SkyrimNet not ready), diary books pause for the session instead of creating a second set; SaveCallback no longer opens a DB during the post-load wait. The latest volume no longer ends in a blank page when a newer entry exists. A volume newer than the loaded save that a later save included is given back to the NPC after Keep. Also that day: the kCantTake clears share one timer thread instead of one sleeping thread per book; GetBookForFormID uses a FormID index instead of scanning every volume; the OpenBookMenu hook is a MinHook detour instead of a hand-written prologue decoder; "sealed" means only "hit the entry limit" (QueueSealedVolumeRecovery is now QueueNewEntryRecovery); the co-save writes no records; the version was set to 1.2.0 (released as 2.0.0). Removed on 2026-09-27 as well: the `SkyrimNetDiaries_API` Papyrus script (never shipped working, no callers) and with it the `"chronicled"` field; the unused `SNPD_DiaryStolenFaction` ESP record stays (harmless). The theft prompt's dependency on SkyrimNet's prompt layout is documented in THEFT.md instead of here. Also removed that day: the in-game `ExtraUniqueID` probe, the unused `DPF_API` shim, the `PhysicalDiaryAPI` and `GetStolenFaction` natives, a log-only duplicate container sink and the `SNDC` co-save cache it fed, Dynamic Book Framework-era `.txt` cleanup, and about a dozen uncalled functions.

Fixed on 2026-09-28 (2.0.0): Dynamic Persistent Forms is replaced by runtime forms the engine saves itself (see [BOOK_FORMS.md](BOOK_FORMS.md)). This removed the DPF workarounds (create queue, FormID claims, pending creations, `kCantTake` timer, VR `sourceFiles` fix, `persisted_in_save` and the inventory re-add) and fixed two issues: **Reset left books in unloaded cells as orphans showing their template's text** (books are now retired: every copy is removed as soon as it can be reached, at retirement or when its cell loads; the invisible form stays in the save), and **a DPF FormID could mean different diaries in different saves** (a book's FormID now belongs to one save's timeline, and the save's own record says which volume it is). The `OpenBookMenu` hook is gone too: the `GetDescription` hook now gives the book menu its text.

## Likely bugs (user-facing)

1. **A new entry is dropped when the NPC doesn't hold their latest volume and the entry isn't dated after it.** When the NPC lost the latest volume (stolen, traded), new entries start a new volume, but only entries dated strictly after its last entry. Anything dated at or before that is logged ("not added to a book") and dropped (`UpdateDiaryForActorInternal`, see [VOLUMES_AND_SYNC.md](VOLUMES_AND_SYNC.md#when-an-entry-arrives-updatediaryforactorinternal)). Two ways in:
   - **Keep, then steal.** After loading an earlier save with Keep, the latest volume can hold entries dated in the future. Steal it, and the NPC's next entry is dated before those, inside the stolen volume's range. Common: Keep and theft are both everyday actions. (The other order is fine: steal, then load a save from before the volume existed, then Keep, and the book is recreated and the theft record is dropped.)
   - **Same moment.** The new entry has the same game time as the stolen volume's last entry. That case alone could start the new volume with tie data, as overflow volumes do.

   More generally, after a Keep new entries go into whichever volume's date range covers them: a finished volume gains a page in the middle (possibly past `EntriesPerVolume`), an entry dated inside an earlier volume only shows when that book is opened, and a stolen copy grows pages the NPC wrote after it was taken.

   **Deferred (uncommon enough for now).** The planned fix splits volumes by write order (`creation_time`, which only moves forward) instead of game date: every new entry goes on the next free page of the latest volume, or starts a new one if that is full or not held; finished volumes never change; the "dated inside" path disappears. After a Keep the dates in a diary run backwards once, at the rewind, which is the honest record. The title page should then show the earliest and latest date, not the first and last page. It needs a SkyrimNet query by write time (see below) to stay cheap, plus a one-time migration of DiaryDB's date boundaries to `creation_time` bounds.

SNPD's own editor re-renders after saving. SkyrimNet API v11 gives entries an `updated_at` to compare against.

## Waiting on a SkyrimNet API

SkyrimNet public API v11 (not released yet; built on the SkyrimNet branch `zev-api-additons`) adds both of these (`PublicGetTimelineState` and the `SkyrimNet_TimelineResolved` ModEvent, `PublicGetDiaryEntriesByWriteTime`), plus the diary edits the editor uses.

3. **`TimelineGate` is a stopgap.** It recognises SkyrimNet's keep/clear prompt by its message text (from the `skynet_DeleteHistoryMessage` form), wraps its callback through a `QueueMessage` hook SkyrimNet also uses, predicts whether the prompt will appear by copying SkyrimNet's rule, polls up to 10 s for a Clear's deletions to finish, and gives up after 30 s if a predicted prompt never shows. A SkyrimNet API such as `PublicGetTimelineState()` (none / pending / kept / cleared, pending until a Clear has finished deleting) would replace all four with one poll; keep the hook only as the fallback for older SkyrimNet versions. See [VOLUMES_AND_SYNC.md](VOLUMES_AND_SYNC.md#waiting-for-the-decision-timelinegate).
4. **A diary query by write time**, for the write-order fix to #1. `PublicGetDiaryEntries` filters by `entry_date` and sorts newest-date first (`ORDER BY entry_date DESC LIMIT n`), so after a Keep no date range covers "the entries written between X and Y". Without it SNPD would fetch every entry the NPC has ever written on each update and book open (hundreds of KB of JSON for a heavily used companion). Wanted: a `creation_time` range filter and order, e.g. `PublicGetDiaryEntriesByWriteTime(formId, fromCreationTime, toCreationTime, limit)` in API v11. SNPD would keep date queries on older SkyrimNet.
